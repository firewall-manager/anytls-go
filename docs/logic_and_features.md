# AnyTLS 逻辑功能说明

本文档详细说明 AnyTLS 项目的代码逻辑、核心功能和适用场景。

## 项目概述

AnyTLS 是一个旨在缓解**嵌套 TLS 握手指纹识别**（TLS in TLS）问题的代理协议。当你在 TLS 连接内部建立另一个 TLS 连接时（例如使用代理访问 HTTPS 网站），外层 TLS 的数据包特征可能与正常的 HTTPS 流量存在差异，从而可能被深度包检测（DPI）系统识别。

AnyTLS 通过以下机制来缓解这一问题：

1. **灵活的填充策略**：通过控制数据包长度和时序，模拟真实 TLS 流量特征
2. **连接复用**：在单个 TLS 连接上复用多个代理流，减少握手开销
3. **动态特征更新**：服务器可以动态调整流量特征，降低被识别的风险

### 核心组件说明

#### 1. Session（会话层）

**位置**：`proxy/session/session.go`

**功能**：
- 管理多个 Stream（流）的生命周期
- 在单个 TLS 连接上复用多个代理请求
- 处理会话层的协议帧（SYN、PSH、FIN 等）

**关键逻辑**：
- 客户端创建新 Session 时会立即发送 `cmdSettings` 帧，包含协议版本和填充策略 MD5
- 服务器收到 `cmdSettings` 后，检查客户端的填充策略是否与服务器一致
- 如果不一致，服务器发送 `cmdUpdatePaddingScheme` 要求客户端更新
- Session 通过帧类型（command）来区分不同的操作：
  - `cmdSYN`：客户端请求打开新流
  - `cmdPSH`：数据传输
  - `cmdFIN`：关闭流
  - `cmdWaste`：填充数据
  - `cmdSettings`：客户端设置
  - `cmdUpdatePaddingScheme`：服务器更新填充策略

**复用机制**：
- 客户端维护一个空闲 Session 池
- 新请求优先从池中获取空闲 Session，而不是创建新连接
- 定期清理超时的空闲 Session（默认 30 秒空闲超时）

#### 2. Stream（流层）

**位置**：`proxy/session/stream.go`

**功能**：
- 每个 Stream 代表一个独立的代理连接
- 实现 `net.Conn` 接口，透明地处理数据传输
- 管理流的生命周期（打开、传输、关闭）

**关键逻辑**：
- Stream 内部使用管道（pipe）机制传递数据
- 客户端写入 Stream 的数据会被封装成 `cmdPSH` 帧发送
- 服务器收到 `cmdPSH` 帧后，将数据写入对应的 Stream 管道
- Stream 关闭时会发送 `cmdFIN` 帧通知对端
- 支持版本 2 协议的握手确认机制（`cmdSYNACK`）

#### 3. Client（客户端会话管理）

**位置**：`proxy/session/client.go`

**功能**：
- 管理所有客户端 Session 的创建和复用
- 实现会话池机制，提高连接效率
- 定期清理超时的空闲会话

**关键逻辑**：
```go
// 创建新流的流程
1. 检查是否有空闲 Session（优先使用最新的，即 Seq 最大的）
2. 如果没有，创建新 Session 并建立 TLS 连接
3. 在新 Session 上创建 Stream
4. Stream 关闭后，如果 Session 未关闭，将其放回空闲池
```

**会话池策略**：
- 使用跳表（SkipList）存储空闲 Session，按 Seq 降序排列
- 优先复用最新的 Session（Seq 最大的）
- 定期检查（默认 30 秒），关闭空闲时间超过阈值（默认 30 秒）的 Session
- 至少保留 `minIdleSession` 个空闲 Session（默认 5 个）

#### 4. Padding（填充策略）

**位置**：`proxy/padding/padding.go`

**功能**：
- 通过填充数据包来模拟真实 TLS 流量特征
- 控制数据包的长度和时序
- 支持服务器动态更新填充策略

**填充策略格式**：
```
stop=8                    # 只处理前 8 个包（包 0-7）
0=30-30                  # 包 0：固定 30 字节（用于认证）
1=100-400                # 包 1：100-400 字节随机
2=400-500,c,500-1000    # 包 2：先 400-500 字节，然后检查(c)
                        # 如果还有数据，继续发送 500-1000 字节
3=9-9,500-1000          # 包 3：先 9 字节，然后 500-1000 字节
4=500-1000              # 包 4：500-1000 字节
...
```

**关键逻辑**：
- 包计数器从 0 开始，每次调用 `writeConn` 递增
- 包 0 用于认证阶段，不支持分包
- 包 1 通常是 `cmdSettings` + 首个 Stream 的 `cmdSYN` + 目标地址
- 包 2 开始是实际代理数据
- 如果用户数据在分包完成前发送完毕，发送 `cmdWaste` 帧填充剩余空间
- 检查标记 `c` 表示：如果上一个分包后没有剩余数据，则停止后续填充

**动态更新机制**：
- 客户端首次连接使用默认填充策略
- 服务器检测到客户端策略不一致时，发送 `cmdUpdatePaddingScheme`
- 客户端收到后更新策略，后续新 Session 使用新策略
- 这样可以最小化使用旧特征的连接数量

#### 5. 认证机制

**位置**：
- 客户端：`cmd/client/myclient.go` 的 `createOutboundConnection`
- 服务器：`cmd/server/inbound_tcp.go`

**流程**：
```
客户端：
1. TLS 握手完成后，立即发送认证数据：
   ┌─────────────────┬──────────┬──────────┐
   │ sha256(password)│ padding0 │ padding0 │
   │   32 字节       │ length   │  数据    │
   └─────────────────┴──────────┴──────────┘

2. 发送 cmdSettings 帧（包含版本、客户端信息、填充策略 MD5）

服务器：
1. TLS 握手后，读取第一个数据包
2. 验证密码哈希
3. 如果认证失败，关闭连接或 fallback 到 HTTP 服务
4. 如果认证成功，进入会话循环
```

## 协议流程详解

### 客户端建立连接流程

```
1. 本地应用发起代理请求
   ↓
2. Inbound 接收连接 (cmd/client/inbound.go)
   ↓
3. Client.CreateStream() 创建流
   ├─ 检查空闲 Session 池
   ├─ 如果没有空闲，创建新 Session：
   │  ├─ dialOut() 建立 TCP 连接
   │  ├─ TLS 握手
   │  ├─ 发送认证数据（密码哈希 + padding0）
   │  └─ 发送 cmdSettings 帧
   └─ 在新 Session 上创建 Stream
   ↓
4. 向 Stream 写入目标地址（SocksAddr 格式）
   ↓
5. 开始双向数据代理
```

### 服务器处理请求流程

```
1. 接收 TLS 连接
   ↓
2. TLS 握手
   ↓
3. 读取认证数据，验证密码
   ├─ 失败：关闭连接或 fallback
   └─ 成功：创建 Session，进入接收循环
   ↓
4. 接收 cmdSettings 帧
   ├─ 检查填充策略 MD5
   ├─ 如果不一致，发送 cmdUpdatePaddingScheme
   └─ 如果版本 >= 2，发送 cmdServerSettings
   ↓
5. 接收 cmdSYN 帧（客户端请求打开流）
   ↓
6. 创建 Stream，调用 onNewStream 回调
   ↓
7. 读取目标地址（SocksAddr）
   ↓
8. 建立到目标服务器的连接
   ├─ 如果版本 >= 2，发送 cmdSYNACK（成功/失败）
   └─ 开始双向数据代理
   ↓
9. 代理完成后关闭 Stream，但保留 Session
```

### 数据包填充流程

```
客户端发送数据时（Session.writeConn）：

1. 检查是否需要填充（sendPadding && pktCounter < padding.Stop）
   ↓
2. 获取当前包的填充策略（GenerateRecordPayloadSizes）
   ↓
3. 对于策略中的每个大小：
   ├─ 如果用户数据 > 策略大小：
   │  └─ 发送策略大小的数据，剩余数据继续处理
   ├─ 如果用户数据 <= 策略大小：
   │  └─ 发送所有用户数据 + 填充（cmdWaste 帧）
   └─ 如果遇到检查标记 'c'：
      └─ 如果没有剩余数据，停止后续填充
   ↓
4. 如果还有剩余数据，直接发送（超出 stop 范围）
```

## 适用场景

### 1. 网络代理和翻墙工具

**场景描述**：
- 需要突破网络审查和封锁
- 在受限网络环境中访问被屏蔽的网站和服务

**为什么适合**：
- 通过填充策略模拟真实 TLS 流量，降低被 DPI 识别的风险
- 连接复用机制减少握手开销，提高响应速度
- 动态更新机制可以快速适应新的封锁策略

### 2. 企业内网代理

**场景描述**：
- 企业需要在安全策略严格的内网环境中提供代理服务
- 需要在不触发安全告警的情况下传输流量

**为什么适合**：
- TLS 加密保证数据传输安全
- 填充策略可以隐藏代理特征
- 支持标准的 SOCKS5 协议，兼容性好

### 3. 数据采集和爬虫

**场景描述**：
- 需要大量代理 IP 进行数据采集
- 需要避免被目标网站识别为代理流量

**为什么适合**：
- 填充策略可以使流量看起来像正常用户访问
- 连接复用减少资源消耗
- 支持高并发连接

### 4. 游戏加速和网络优化

**场景描述**：
- 游戏玩家需要通过代理优化网络路径
- 需要稳定的低延迟连接

**为什么适合**：
- 连接复用减少连接建立延迟
- 支持 TCP 和 UDP（通过 udp-over-tcp）协议
- 可以针对不同场景调整填充策略，平衡性能和隐蔽性

### 5. 科研和测试环境

**场景描述**：
- 研究网络协议和 DPI 检测机制
- 测试不同流量特征的效果

**为什么适合**：
- 填充策略可配置，便于实验
- 支持动态更新，可以快速测试不同策略
- 代码开源，便于研究和改进

## 技术特点

### 优势

1. **灵活的填充策略**
   - 支持精确控制每个数据包的长度
   - 支持范围随机，增加流量多样性
   - 支持检查标记，智能停止填充

2. **高效的连接复用**
   - 单个 TLS 连接承载多个代理流
   - 减少 TLS 握手开销
   - 智能会话池管理

3. **动态特征更新**
   - 服务器可以远程更新客户端填充策略
   - 最小化使用旧特征的连接数量
   - 快速适应新的封锁策略

4. **版本协商机制**
   - 支持协议版本协商
   - 向后兼容旧版本客户端
   - 可以逐步启用新特性

5. **完善的错误处理**
   - 支持握手失败通知（v2）
   - 支持心跳检测（v2）
   - 支持超时检测和恢复

### 限制和注意事项

1. **TLS in TLS 开销**
   - 嵌套 TLS 会增加数据包大小
   - 可能导致 MTU 限制问题
   - 无法完全消除这种开销

2. **下行流量处理**
   - 当前版本主要处理上行流量特征
   - 下行流量特征未做处理
   - 可能成为识别点

3. **主动探测**
   - 非 HTTP 服务器可能面临主动探测
   - 需要实现 fallback 机制

4. **统计特征**
   - 即使单个包特征正常，时序和包数量仍可能暴露
   - 需要更复杂的策略来处理

## 总结

AnyTLS 通过巧妙的填充策略和连接复用机制，在保持高性能的同时，有效缓解了 TLS in TLS 指纹识别问题。其动态更新机制使得协议可以快速适应新的封锁策略，是一个在受限网络环境中非常有用的代理协议。

虽然协议不能完全消除所有识别风险，但通过合理的配置和使用，可以在性能和隐蔽性之间取得良好的平衡。对于需要在网络审查环境中使用的场景，AnyTLS 提供了一个可靠且灵活的选择。
